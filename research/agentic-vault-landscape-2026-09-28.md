# Agentic vault: external design patterns and gaps

Research date: 2026-09-28. This note compares the proposed canonical Markdown vault, schema validator, optimistic concurrency control (OCC), event log, watcher, and Bestie/Philip roles with the first-party [obsidian-second-brain repository](https://github.com/eugeniughelbur/obsidian-second-brain) and [Obsidian Help](https://obsidian.md/help). It is a design review, not evidence that the local workflow has been implemented or exercised.

## What the reference project actually offers

- **Portable memory contract.** Its [AI-First Note Spec](https://github.com/eugeniughelbur/obsidian-second-brain/blob/main/AI-FIRST.md) calls for a self-contained summary, stable preamble, typed frontmatter, dates on changeable claims, source URLs, links, confidence levels, and treating retrieved text as data. Its longer [rules](https://github.com/eugeniughelbur/obsidian-second-brain/blob/main/references/ai-first-rules.md) distinguish source claims from inference and warn about false claims that a note is absent. **Inference:** use these as *content quality checks* alongside the local schema, with the exact required fields and exceptions written down; do not silently adopt a second competing schema.
- **Single source for agent surfaces.** The project's [architecture](https://github.com/eugeniughelbur/obsidian-second-brain/blob/main/architecture.md) describes platform-neutral command definitions compiled to CLI-specific adapters, with generated outputs treated as artifacts. **Inference:** one canonical role/workflow contract and generated installation surfaces would reduce drift among Claude, Gemini, and other agents. Add a conformance check comparing installed skill links/content to that source.
- **Deterministic checks around agent prose.** Its [skill](https://github.com/eugeniughelbur/obsidian-second-brain/blob/main/SKILL.md) says the optional MCP write path validates notes, updates the index, logs the operation, and can run a post-write command; the repository also has a [write-time validator](https://github.com/eugeniughelbur/obsidian-second-brain/blob/main/hooks/validate-ai-first.sh). **Inference:** put all vault mutations through the local engine's schema, OCC, and event boundary regardless of which agent initiates them. Hooks alone cannot cover direct filesystem edits.
- **Source preservation and temporal truth.** The [skill](https://github.com/eugeniughelbur/obsidian-second-brain/blob/main/SKILL.md) specifies immutable raw sources and bi-temporal history for changing facts. **Inference:** Bestie and Philip outputs should carry stable source references, observed/valid time, retrieval time, and a clear distinction between quotation, finding, and recommendation. Keep bulky evidence in sidecar artifacts rather than inflating every note's frontmatter.
- **Recall needs a measurable path.** The [README](https://github.com/eugeniughelbur/obsidian-second-brain#readme) describes incremental search, a retrieval evaluation command, health checks for stale claims, duplicates, orphans and broken links, and bounded session context. **Inference:** define a small recall benchmark and context budget before adding embedding infrastructure. A successful write loop alone does not establish that future agents can find the right note.

## Obsidian constraints to reflect in the plan

- Obsidian [Properties](https://obsidian.md/help/properties) support simple typed values but not nested properties in the normal editor; nested YAML is best viewed in source mode. **Inference:** keep user-edited top-level properties flat (`type`, `status`, `owner`, `updated`, `tags`), put rich agent evidence in body sections or linked artifacts, and validate one property name to one type across the vault.
- [Bases](https://obsidian.md/help/bases) is a core plugin that filters and edits local Markdown files through their properties; `.base` files define views. **Inference:** use Bases for human triage/status views only after the canonical status fields are stable. The engine remains the authority for transitions and multi-file commits; a Base edit is another concurrent writer and must be detected by OCC.
- [Obsidian Sync version history](https://help.obsidian.md/Obsidian%2BSync/Version%2Bhistory) can help restore versions, but that is a user-facing recovery feature. **Inference:** it does not replace the vault's atomic transaction, event identity, idempotency, or conflict policy.

## Related skill models

- [kepano/obsidian-skills](https://github.com/kepano/obsidian-skills) keeps focused Agent Skills for Obsidian Markdown, Bases, Canvas, and CLI usage in the portable `SKILL.md` format. **Inference:** keep vault-format guidance separate from the triage workflow, so every agent can reuse it without duplicating syntax rules in each role prompt.
- [georgeracu/obsidian-agent-vault](https://github.com/georgeracu/obsidian-agent-vault) uses a shared `AGENTS.md` entry point, five typed agent-memory records, a stale-memory review queue, lazy-loaded skills, and a read-only memory lint. **Inference:** a small shared context contract and a human-visible stale/failed queue would make the vault easier to resume and supervise across agents. Its optional semantic index is a later scale choice, not a prerequisite for a reliable triage loop.

## Gaps to resolve before calling the loop end-to-end

1. **Agent result contract.** Define versioned JSON output per role: run ID, note ID, input revision, role/version, status (`complete`, `partial`, `failed`), observations, evidence references, confidence, timestamps, and error details. Validate and store each result before aggregation. A scalar fixed score is insufficient evidence of research.
2. **State machine and failure semantics.** Specify transitions from captured item through dispatch, role results, aggregation, human review, and committed note. Document timeout, retry, duplicate delivery, crash recovery, partial result, and stale-revision behavior. Every transition needs a persistent event and an idempotency key.
3. **Separation of authority.** Let Bestie and Philip propose findings; make one coordinator/engine the only writer of canonical notes. State which fields humans may edit directly in Obsidian and how those edits invalidate pending agent work. Avoid agents independently rewriting a shared note.
4. **Evidence and decision policy.** Define how conflicting agent findings are represented, what the scorer can infer, when the loop abstains, and when a human must approve a destructive or low-confidence change. Preserve rejected findings and provenance in artifacts instead of overwriting them.
5. **Demonstrable acceptance test.** Use a fixture with a real source, invoke both role adapters (or explicit test doubles with contract-equivalent artifacts), assert artifact provenance and score derivation, modify the note mid-run to prove OCC rejection, then retry safely. Assert the final note, status view, and event log agree. Build the tested binary from current source, and clean up fixture files and events together.
6. **User experience and scale.** Start with a small command vocabulary (capture, inspect, triage, approve, recover), readable status/error messages, and one dashboard generated from canonical metadata. Add bounded queues, leases, backpressure, per-agent resource limits, observability, and periodic repair checks before unattended high-volume scheduling.

## Adoption boundary

The reference repository's [architecture document](https://github.com/eugeniughelbur/obsidian-second-brain/blob/main/architecture.md) says it was last reviewed against a June 2026 commit and has inconsistent command counts with the current [README](https://github.com/eugeniughelbur/obsidian-second-brain#readme). Treat its operational claims as patterns to inspect, not proof of production correctness. The most transferable elements are explicit note provenance, one cross-agent contract, and deterministic write validation; the local engine's OCC and event design should remain the transaction authority.

## Decision on the linked repository

**Revised recommendation given the desired full second-brain feature set: evaluate this repository as the primary skill and experience layer, not merely as inspiration. Keep the existing vault intact during the evaluation, and establish explicit ownership for every note class before connecting writes.** Its [architecture](https://github.com/eugeniughelbur/obsidian-second-brain/blob/main/architecture.md) states that runtime commands read and write plain Markdown, with a write-validation hook specific to Claude Code. Its [`obsidian-save` command](https://github.com/eugeniughelbur/obsidian-second-brain/blob/main/commands/obsidian-save.md) asks parallel agents to update multiple linked notes. That is a different write model from this vault's single canonical writer with OCC and audit events. This is a compatibility inference from the documented commands, not a claim that its code is defective.

The desired feature scope spans [operations and thinking tools](https://github.com/eugeniughelbur/obsidian-second-brain#47-commands), [progressively loaded session context](https://github.com/eugeniughelbur/obsidian-second-brain/blob/main/commands/obsidian-world.md), [multi-source ingest](https://github.com/eugeniughelbur/obsidian-second-brain/blob/main/commands/obsidian-ingest.md), research, and optional scheduled maintenance. A five-command replacement would miss the product goal. The integration design should distinguish engine-owned structured records (ideas, projects, areas, decisions that drive transitions) from knowledge notes that the skill layer may manage, or route both through an expanded engine. Do not leave this ownership implicit.

| Capability group | Recommendation | Initial boundary |
|---|---|---|
| Capture, daily notes, decisions, session continuity, find, export, health | Pilot early from the upstream skill layer | Search before create; preserve source and note identity |
| Challenge, connect, distill, review, pattern discovery | Pilot after recall quality is measured | Read-only output first; persist findings with provenance |
| Ingest, synthesize, reconcile, graduate | Pilot as proposed diffs before automatic multi-note writes | Show affected notes, evidence, conflicts, and an approval/retry path |
| Web, video, podcast, and vault-grounded research | Install by source/need, not as one mandatory stack | Explicit provider, cost, upload, and source-retention settings |
| Background recall and scheduled agents | Enable only after foreground workflows are repeatable | Bounded context, opt-in schedules, visible run logs, rollback/recovery |

For notes viewed in Obsidian, combine an agent-facing summary with readable human content. The upstream AI-first preamble is useful; treating human readability as expendable would conflict with the stated user-friendly goal. For time-changing claims, begin with source URL, `observed_at`, `valid_as_of`, and supersession links; reserve full bi-temporal machinery for cases that demonstrate a need.

| Candidate | Use here | Gate |
|---|---|---|
| AI-first note summaries, source dates, confidence, links | Adapt into the existing idea and knowledge schemas, with readable human sections | One authoritative schema; source and inference remain distinguishable |
| `/obsidian-find`, search-before-create, retrieval evaluation | Pilot on an isolated vault copy; keep the search index rebuildable | Known-note recall and duplicate-detection fixtures with bounded latency |
| Cross-CLI generated adapters | Adapt the single-source build pattern for Olivier, Bestie, Philip, and vault commands | Installed Claude/Gemini/Codex surfaces pass the same contract tests |
| `/obsidian-health` | Adapt read-only checks for stale claims, broken links, invalid properties, and orphan artifacts | Findings are severity-ranked; repair is a separate reviewed operation |
| `/obsidian-save` and automatic multi-note rewriting | Defer direct adoption; route proposed changes through the engine | Concurrent human and agent edits produce OCC conflicts, never silent overwrites |

**Evaluation spike:** install the reference repo only in a temporary sample vault. Exercise capture/save, find, and health on the same small set of notes; record which files each command changes, what provenance it leaves, and whether a second CLI reproduces the behavior. Prototype one adapter that turns a proposed note change into a `read-record`/`commit` transaction. A successful spike produces a compatibility matrix and an explicit adopt/adapt/defer decision before broad installation.
